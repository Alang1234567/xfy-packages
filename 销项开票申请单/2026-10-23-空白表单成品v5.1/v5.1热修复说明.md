> 对象包：`销项开票申请单_实例化表单_v5.1.zip`（21,901 B，SHA-256 `1ea07e63eae3de207479ea2a3159131bd4602f3a0aa1c663fadc32dc5e5621a5`；内层 iform SHA-256 `82e80d95bd75703da9ae8d176428da2f5ba0c9a2e24bc419ca459ea1cff723e3`）
> 基线：v5 成品包（SHA-256 `8471dfa2…`）。**本版只修一个缺陷及同类隐患，功能口径、宏 SQL、服务端写回逻辑逐字未动。**
> 现场现象（Alan 2026-10-26 实测 v5）：提取、主从联动、勾选级联、已勾选金额均正常；点「保存申请」弹 `"dentid"未定义`，保存中断。

## 一、根因：dentid 是什么、缺在哪

`dentid`（企业 ID）**不是平台注入的全局变量**，而是部分原厂表单**自备的表单级局部变量**——要用必须由表单自己声明并赋值。生产证据有两条现成惯例：

1. **业务员表单 `0rph77yz9b485m6q`**：文件头 `var dentid;` 显式声明，`uf_onLoad` 里 `dentid = form.userinfo.entid;`（登录信息里的企业 ID；打开已有单据时再被 `form.args.entid` 覆盖）。
2. **参照表单 15dka 本人**：不用该变量，它的百望重发链路直接取**主数据集当前行的 `EntId` 字段**（`params.K_EntId = ds_InvoQueryMt.field("EntId").value`）。

而客户资料 `2p1teo4k24z55h5x` 通篇裸用 `dentid` 且从不声明——这是厂商自己的缺陷模式，项目《自查报告-2026-10-21》早已点名：「未声明变量 dentid（9 处）…平台未注入则多条路径抛 ReferenceError」。本包 v1 建造时照客户资料的写法把裸读移植了进来，又没有照业务员表单补声明与赋值，等于把缺陷原样继承。

全语料复核：`dentid` 在整个 harvest 语料（15dka 全份真值 + 185 个函数库函数明文）中**零出现**，不存在「平台某处会给它赋值」的任何痕迹；Alan 的实测则直接坐实本运行时不注入。

缺失位置：客户端 `main.js` 在组装服务端参数时有 **4 处** `params.K_EntId = dentid;`，无任何声明/赋值在前。该语句位于各函数的 try 块**之外**（参数先组装、后才调用服务端），裸读抛出的 ReferenceError 无人接管，直接以平台网页消息形式弹给用户——即现场看到的报错。四处所在的函数全部是保存/撤销入口，所以表现为「提取一切正常、一保存就报错」。

## 三、模拟为何没测出（第二次同类漏检的整改）

v4.1 的「grid_list 未定义」之后，这是第二次「本地全绿、现场未定义」。这次有**两道防线同时失效**：

**失效一：fixture 的 harness 替身把缺失盖住了。** v5 fixture 在装配运行时替身时有一行 `global.dentid = "ENT1";`——恰好替包里补上了真实运行时不存在的全局，保存/撤销链于是全绿。对账（harness 预置项 ↔ 真实定义集）：

| harness 预置项 | 真实来源 | 判定 |
|---|---|---|
| ds_qry / ds_mt / ds_dt / ds_rmt / ds_rdt / ds_qmt / ds_qdt | XUL datasetobject id | 合法替身 |
| tabcontrol1 / combobox7 / combobox8 / label13 / textbox4 / sel_SaleMan | XUL 元素 id | 合法替身 |
| toolbar / form / FormUtil / Utility | 平台全局（15dka 等生产表单在用） | 合法替身 |
| pf_GetStaffFactory / pf_GetStaffYwlx | 平台客户端函数库（15dka 实际调用） | 合法替身 |
| DBUtil | 服务端平台对象（函数库明文在用） | 合法替身 |
| alert / confirm | JS/浏览器内建 | 合法替身 |
| **dentid** | **任何定义集都不存在** | **就是它盖住了缺陷** |

差集 = { dentid } ≠ ∅——当时没有这项检查，差集无人看。

**失效二：audit_refs 的引用对账有两个盲点。** (a) 白名单里有一条 dentid，注解写着「平台全局企业 ID 变量、原厂客户资料通篇裸用」——把厂商的缺陷模式误当成平台惯例；(b) 更根本的是，对账只收集 `IDENT.` 形式的对象头引用，而 `= dentid;` 是**裸值读**，根本不进引用集——那条白名单从未被真正检验过。

**整改（已落地为固定检查，后续每版强制跑）：**

1. audit_refs 白名单剔除 dentid 并注明证伪过程；新增**裸标识符读扫描**：剥离注释/字符串/正则后，main.js 与 server.js 里每个裸读都必须可归因（包内声明 / XUL id / 平台白名单 / JS 内建），不可归因即 FAIL。本次顺带修正了扫描器的一个正则缺陷（函数名含数字时参数提取漏检，如 uf_pad2 的形参 n）。
2. audit_refs 新增**参数契约对账**：客户端在调用 executeServerScript 的函数体内赋值的 `params.K_*` 键集，必须与 server.js 实际读取键集相等（本次四键 K_EntId/K_User/K_Rows/K_Dir 全等）。
3. verify 新增固定项「**harness 替身差集 = 空**」：fixture 的 `global.X =` 预置集必须 ⊆（XUL ids ∪ 平台白名单 ∪ 内建），且显式断言 dentid 不在预置集内。
4. **阴性对照**（证明新防线真的拦得住）：升级后的 audit 对 **v5 旧包**运行，恰好只报一项 FAIL——`main.js 中 dentid ×4 不可归因`；v5.1 的 fixture harness 指向 v5 旧包时，在保存第一步即以 `dentid is not defined` 中断退出（与现场同症）。
