## 一、失败一：pf_showWaitBox 运行时未定义

### 根因（元数据取证）

v7 把保存/挂账两入口改调平台共享库函数 `pf_showWaitBox`，依据是它在 designer 函数清单（`designer.openFuncList` 拉回的 185 个函数）中在册。逐列比对清单元数据：pf_showWaitBox 与运行时确可调用的 pf_chkBal、pf_fieldCompute **逐列相同**（库别 SCM、类别「供应链」、启用 Y、服务端 N），其登记注释里甚至带着官方示例 `ret = pf_showWaitBox(uf_subQuery);`——正是 v7 的调用方式。结论只有一个：

> **设计器函数清单是函数库的主注册表，不等于表单运行时的装载集。** 运行时可用的 pf_ 函数是被 protected 核心链引用到的那些；pf_showWaitBox（2016 年的显示等待提示工具函数）从未被核心链引用，未装载进本表单运行时，故调用报「未定义」。元数据上没有任何字段能区分这一点——清单在册 ≠ 运行时可用，引用库函数前必须验运行时作用域。

### 修法

把 pf_showWaitBox 的**真实函数体移植进表单本地**，改名 `uf_showWaitBox`（避免与库名冲突）：逐行忠实移植其 DOM 遮罩（div#editBehaviorDiv + iframe#loadMask）/等待框/1 秒定时/出错 alert/finally 必拆逻辑，仅改函数名；其体内只用 document/navigator/setTimeout/alert，无其它库依赖，无需连带移植。保存（uf_djsave）与挂账（uf_djgz）两入口改调本地版。verify 已证：移植体与库原体**去空白后逐标记一致（仅函数名不同）**。

## 二、失败二：零量弹框仍触发

### 根因（源码取证）

弹框本体在函数库 `pf_fieldCompute` 的 `case "num"` 分支，逐字摘录其全部门控：

```js
case "num":
    if (num == 0 && cancelNum == 0) {
        alert(Utility.getMessage("numEqualZero"));   // 「当前商品数量为零,注意!」
        pass_hjjy = false;
        setTimeout(function(){ dataset.grid.currentCol = _fldIndex(dataset, "num"); }, 7);
    }
```

**没有其它门控**：不读 verifyDisabled、不读任何 form 参数开关（它读的 advance 参数只有计价方式 jsfs、扣率来源 JGFROMKL、零价允许 alwzp、改价权限 canModAmt，与本分支无关）。

而 protected 的 `sys_compute` 尾部是**无条件调用** `pf_fieldCompute(ds_ddmx, field, "", 1)`——verifyDisabled 只门控 sys_compute 内部的库存校验段（kf_chkBal/pf_chkBal 的调用条件），对 pf_fieldCompute 无效。

### v6/v7 建模失误复盘（如实）

v6 把弹框误判在 pf_chkBal 体内（当时库体不可读，按文案全仓零命中推断），据此设计了「verifyDisabled 抑制」路线；v7 沿用。两轮 mock 都通过，是因为 harness 里的 pf_chkBal 是**按该错误模型写的行为桩**——等于用假设证明假设。函数库真体到手后逐条核对：抑制从未对 pf_fieldCompute 生效，v6/v7 的摘除在真实运行时必然失败，现场截图与此完全吻合。本轮起立规：弹框类断言必须以目标函数真实门控为准，harness 必须装入真实函数体（见第四节）。

### 修法：守卫 uf_numCompute（统一收口）

```js
function uf_numCompute(){
    // num==0 且 cancelNum==0 且 TaxPrice>0 → 改走 sys_compute("taxPrice") 触发同一套金额写回
    // num==0 且 TaxPrice 同为 0 → 不走 taxPrice(其零价分支按 alwzp 参数可能另弹价格提示),
    //   按 pf_fieldCompute 在 num==0 时的净写回直写金额族归零(taxAmount/amount/tax/baseNum/retailAmt)
    // 其余情况(num>0 或 cancelNum>0) → 原样 sys_compute("num")
}
```

等价依据（均以真体核对）：pf_fieldCompute 的金额写回段与触发字段无关——num==0 时 "num" 与 "taxPrice" 两分支写回集逐项一致（taxAmount/amount/tax/baseNum/retailAmt/price 等），差异只在弹框、pass_hjjy 属性与抢焦点三项副作用；扣率重算 JGFROMKL 仅在参数 =="Y" 时发生（本表单未置）；pf_chkBal 在 field=="taxPrice" 时行校验路径不动作。守卫另在与 pf_chkBal 相同门控下（未抑制、angleid 非空、balChkTime>1）补写其暂存动作 `tmpNum = Num`，使该校验暂存字段的残留与旧链逐字一致（sys_compute 的整单限量回退分支会读它）。

**一处如实说明的语义差异**：旧链在零量计算后会把数据集属性 pass_hjjy 置 false，使 sys_beforePost 提前放行其余行检；新链该属性保持 true，beforePost 的行检照常执行——方向是**更严**，且保存校验（uf_saveCheck「数量必须大于0」）独立拦截零量行、逐字未动，不影响出单正确性。

## 三、A 方案：编辑期清零 + 非模态提示行（Alan 拍板定稿）

- **控件**：main.xul 新增只读标签 `lbl_qtytip`，红色文字，位于明细网格上方空带（left:2px; top:190px; width:1100px; height:17px）。落点取证：xul 绝对定位全量扫描证实 top 183–214 × left<1191 区域无任何既有控件，不遮挡、不改既有布局尺寸（网格 grid1 仍在 top:215）。
- **写入**：只经集中处置助手 `uf_editQtyClear(tip)`——清数量族 9 字段 → verifyDisabled 包装走 uf_compute 重算金额 → 写提示。两类编辑期清零共用：
  - 手工录入除不尽：`第X行 数量Y 不能被每袋装量Z整除，已清零`（行号/原数量/每袋装量/已清零四要素齐全）；
  - 改选商品（uf_reselectResetQty 改为委托该助手）：`第X行 更换商品，数量已清零`。
- **生命周期（最终规则）**：新清零事件覆盖旧提示；保存成功后清空（挂在 uf_saveBill 首行——它只在 sys_save 成功路径被调用，校验拦截在其之前提前返回、不会误清）；表单打开（uf_onload）为空；清空当前单据确认通过后清空（工具栏按钮改绑包装 uf_billEmpty，取消确认不动提示）；**录入合规数量不主动清**（防闪烁，提示保留到下一次清零事件或保存成功）。
- **范围不动**：导入路径维持完成弹窗点名，不走提示行；保存校验逐字未动。

## 六、现场验证点（导入后按序验）

1. 录数量 **0** → 不弹「当前商品数量为零」，金额为 0。
2. 录数量 **2**（每袋 0.9 商品）→ 静默清 0，明细网格上方红字提示「第1行 数量2 不能被每袋装量0.9整除，已清零」。
3. 录数量 **1.8** → 保留，金额 99（按价 55 计），提示不被清掉。
4. 改选商品 → 数量清零，提示变为「第X行 更换商品，数量已清零」。
5. 点**保存** → 出现等待框+整屏遮罩（约 1 秒后存盘），毕即消失，**无「未定义」报错**；保存成功后提示行清空。
6. 点**挂账** → 同上。
7. 留一行数量 0 点保存 → 被「数量必须大于0」拦下（等待框随之消失），提示行保留不清。
8. 点「清空当前单据」并确认 → 单据清空，提示行一并清空；取消确认则提示保留。
9. 导入艾叶数据（123 除不尽）→ 仍为完成弹窗点名 + 清零金额归零（口径不变）。
10. 限销客户开单 → 限销仍关闭（protected 未动）。
