# 行校验摘除报告：销售开票「当前商品数量为零,注意!」弹框

**结论先行：弹框已摘除。** 编辑期行校验按 Alan 最新口径保留——数量除不尽「每袋装量」仍当场清 0、金额同步归零，只是**全程静默、不再弹框**；保存校验原样保留，数量为 0 的行保存时照样被拦。

## 弹框出自哪里

「当前商品数量为零,注意!」这句文案，**在我们能改的任何文件里都不存在**：main.js 从原厂快照到 v5 全部版本、portect.txt、server.txt、包内语言文件、平台手册（CHM）全仓检索零命中。它出自**平台共享保护库的库存校验函数 pf_chkBal**——编辑期链条是：数量格录入 →（数据集事件 Num.onsettext）→ `uf_compute()` → `sys_compute("num")` → pf_chkBal。该函数本体在平台保护库里，按既定边界改不动，所以这次用的是**调用侧绕开**：不让它在"数量为 0"时被调用（见下）。

触发面一共三处，前两处是这次摘除的：
1. **手工录入**（Alan 的复现场景）：录入 2（每袋 0.9、除不尽），数量被处理为 0 后，同链的行计算里库存校验见到零数量即弹此框；手工直接录 0 也一样会弹。
2. **我方 v4/v5 的清零路径**：导入收尾、改选商品的"清零+行计算重算"会在数量 0 时调 `sys_compute("num")`，同样撞这个弹框——这是我方新路径增加的触发机会，一并处理了。
3. 保存时不会弹：保存校验的数量拦截（见下）排在系统校验之前，零数量行在进系统校验前就被拦下。

说明一句归属：弹框机制本身是原厂平台的（编辑链与保护库都是原厂件），不是我方代码引入的；我方 v4/v5 的清零重算只是多给了它几次触发机会。

## 摘除方式（只动 main.js 与 main.xul 的一处事件绑定）

- **数量格入口换包装函数**：ds_ddmx 的事件绑定里，Num 的 onsettext 由 `uf_compute()` 改绑新函数 `uf_onNumSetText()`（main.xul 仅此一处变化，其余逐字节不变）。新函数做三件事：
  - 手工录入时先用共用整除判定判当前行：除不尽 → 静默清零数量族；
  - 随后整段行计算在平台自带的校验抑制开关（verifyDisabled）下执行——数量为 0 时库存校验本无校验对象，跳过它只去掉弹框；金额公式不受该开关影响，照常把金额算归零；
  - 数量合规时不设抑制，行计算及其库存/限销校验与原来完全一致（mock 实证：库存校验以原值实际执行）。
  - 程序化填行期间（粘贴/提取等，抑制开关本就开着）纯透传原函数，导入既有流程一字不变。
- **两条既有清零路径补抑制**：`uf_qtyClearAndRecompute`（导入清零重算）、`uf_reselectResetQty`（改选清零）的重算调用同样加了抑制包装，清零行为本身不变。
- **导入完成弹窗（回执+逐行点名）保留不动**——那是导入结果回执，不是行校验；保存侧的拦截提示也保留。
