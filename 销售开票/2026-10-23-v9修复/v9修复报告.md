## 一、缺陷一：保存成功后等待框滞留

### 根因（代码取证）

把保存全链逐环读通（均为真体）：`uf_djsave → uf_showWaitBox(回调) →[1 秒定时]→ sys_save（protected 明文）→ uf_saveBill（main）→ form.save("prompt")`。

1. **func 链本身正常完成**：sys_save 内层对 uf_saveBill 有自带 try/catch（异常会 alert），其尾部 `textbox2/3.setDisabled(false)` 在 try 外；Alan 现场无任何报错弹窗且保存成功——即回调是正常返回的，故障不在存盘、不在校验。
2. **拆除是单点脆弱链**：v8 移植体（= pf_showWaitBox 库原体）的唯一拆除路径，是定时回调 finally 里两句**裸** `document.body.removeChild(div); document.body.removeChild(divMask);`——串联执行、无 try 包裹、无幂等、无兜底通道。两句中任一句抛错，后一句永不执行，且异常逸出 setTimeout 回调，在现场不产生任何可见报错（与 Alan「无报错、框滞留」的现象严丝合缝）。
3. **首句即抛错的机制**：两句都以「闭包持有的节点仍是 document.body 的直接子节点」为前提。而 appendChild 与拆除之间隔着平台 `form.save("prompt")` 的完整存盘过程（平台存盘层约 4.4 秒）：该过程对表单文档的重渲/刷新会改动 body 的子节点构成，闭包 div 若已非 body 直接子节点，`removeChild(div)` 即抛 NotFoundError——div 不拆、divMask 更轮不到，框与遮罩双双滞留。平台运行时源码不在本地任何材料内（早已定案：不随设计器分发、在客户机 IE 缓存里），存盘过程改动 body 构成的微观一步无法逐字取证，此点如实标注为**由代码结构 + 现象唯一自洽的推断**；但修法不依赖它——见下，任何一种父级变动/拆除抛错都被新实现覆盖。
4. **旁证两条**：(a) 移植体入口预清只清 `#editBehaviorDiv`、**从不清 `#loadMask`**，遮罩本身就只有 finally 这一条拆除路；(b) 本版 mock 的 FI-1 场景在规范化假 DOM 上完整复现了该机制：把框节点改挂到另一父级后，v8 式 `body.removeChild(闭包引用)` 必抛 NotFoundError，而新版拆除顺利通过。另须交代：v8 的 mock 之所以没测出来，是其假 DOM 的 removeChild 被写成「找不到就静默跳过」（宽容假件），把真实 DOM 的抛错语义抹掉了——本版假 DOM 已按规范重做（非子节点必抛错）。

### 修法（自包含 + 多重兜底）

删除 v8 移植体，换表单本地最小自包含实现（式样与库版一致：遮罩 iframe + loading 提示框；仍用 iframe 作遮罩，因网格等窗口化控件只有 iframe 盖得住）：

- `uf_showWaitBox(func)`：入口先扫一遍残留 → 自建 DOM（id 改 `ufWaitDiv`/`ufWaitMask`，避开与库版 id 撞名）→ 武装保底定时器 → 1 秒后执行回调（让浏览器先绘出框，同库版原意），回调毕（成功/校验拦截返回/抛错）finally 必拆；
- `uf_hideWaitBox()`：**按 id 在当前 document 重查、经 `parentNode` 拆除**（不假设父节点是谁，改挂后照拆）；逐个元素 try 包裹、互不连累；可重复调用结果一致（幂等）；顺带清 v8 旧版两 id（`editBehaviorDiv`/`loadMask`）的可能残留；
- **保底通道**：`UF_WAITBOX_MAX_MS = 30000` 一拍，未清干净最多再重试 2 拍（共约 90 秒）。取值依据：现行保存全程约 5.4 秒（含出框 1 秒延时；平台存盘层约 4.4 秒），历史最慢单次保存为优化前约 13.5 秒；30 秒约为现行 5 倍、亦覆盖历史最慢情形，正常保存永远走 finally 通道即时拆除。同步存盘期间 JS 单线程阻塞，定时器只能在存盘返回后触发，不影响存盘本身；个别保存若真超节律，框先退场、仅提示提前消失。
- **一个设计审查拦下的坑**（如实记录）：初稿的 hide 一进门就 clearTimeout 保底定时器——若本次拆除自己抛错（如 FI-2 的查询故障），保底会被误杀、兜底自废。定稿改为：拆除全程无抛错才 disarm 保底；抛错即保留保底待其重试。FI-2 场景专门断言这一点。

### 未采用的冗余点（如实）

任务书要求「若 main.js 里能找到平台保存成功后的既有钩子，再挂一次冗余拆除」——核查结论：保存成功后 main 侧唯一被 protected 调用的钩子是 `uf_saveBill`，但它在 sys_save 内、`form.save` **之前**执行，在那里拆框会让等待框赶在真正存盘前消失，适得其反，故不挂。冗余由「finally + 保底重试 + 下次保存入口预扫」三重构成。

## 二、缺陷二：红字提示未出现 → 改定 alert（Alan 拍板）

### 标签方案取证收尾（三路）

1. **路径在**：手工录入主路径逐环无断点——`Num.onsettext → uf_onNumSetText →（除不尽分支）→ uf_editQtyClear → uf_qtyTip`；改选路径 `uf_reselectResetQty → uf_editQtyClear` 同样汇入。写提示点唯一、确实会被调用。
2. **结构有硬伤**：v8 报告称标签落点为空带，复核 xul 全量坐标后证伪——`lbl_qtytip`（top:190,height:17）与同在 panel1 的三个 checkbox（对接WMS系统/新客/是否自动开具发票，top:189,height:20,left 22/258/521）**整带重叠**，v8 的"空带"扫描漏掉了这三个控件。该行字即便写上，也会被这排 checkbox 压住大半。
3. **写法无平台先例**：`uf_qtyTip` 用 `lbl_qtytip.setText(t)` 与 `lbl_qtytip.value = t` 双写、且两句都套了静默 try/catch（调试期不应静默的老教训，这次栽在自己手里）——函数库明文与其他表单代码中未找到给标签控件这样赋值的真实先例可对照； bare 全局引用控件本身在 protected 里有先例（`textbox2.setDisabled`），故引用方式大概率可达，更可疑的是 setText 并非该平台标签控件的真实 API、`.value` 赋值不触发其渲染文本更新。两句若先后抛错/无效，都会被静默吞掉——现场表现正是「无提示、无报错」。

### 改定与实现（Alan 2026-10-23 11:12 拍板）

- **撤销标签**：main.xul 删除 `lbl_qtytip`、工具栏「清空当前单据」绑定恢复原厂 `sys_billempty`——v9 的 xul 与 v7（服务器真值）**逐字节一致，界面恢复原样**；main 中 `uf_qtyTip`、`uf_billEmpty` 包装函数一并删除，uf_onload/uf_saveBill 里的清提示调用删除。
- **改走 alert**：`uf_editQtyClear` 末步改为 `alert(tip)`——清零字段、重算（抑制下 uf_compute）全部不变，只换最后一步的呈现。文案维持两类逐字不变：「第X行 数量Y 不能被每袋装量Z整除，已清零」/「第X行 更换商品，数量已清零」。alert 落点唯一（verify 静态断言：uf_editQtyClear 内 alert 恰 1 处）。导入路径不变：仍走完成弹窗汇总点名，不逐行弹。
- **防连环弹论证**（任务书要求）：alert 出现在 onsettext/选择回写的流程**末端**（清零+重算都已完成）。点确定关闭后，即便焦点回格、平台再触发一次 onsettext，`uf_onNumSetText` 的除不尽分支以「数量 > 0」为入场前提——此时数量已是 0，不入分支、只走 uf_compute，不会二次清零、不会再弹；改选路径同理（商品切换已完成，回写不会重开选择器）。程序化填行（verifyDisabled）更是纯透传。mock 对三条都加了断言：**单次清零事件 alert 恰 1 次**（S2/S5），重入后仍 1 次（S2-防重入）。

## 六、现场验证点（导入后按序验）

1. 录数量 **0** → 不弹「当前商品数量为零」，金额为 0，**也不弹原因框**（录 0 不是清零事件）。
2. 录数量 **2**（每袋 0.9 商品）→ 数量清 0，**弹原因框「第1行 数量2 不能被每袋装量0.9整除，已清零」恰 1 次**，点确定关闭、不连环弹。

4. 改选商品 → 数量清零，弹「第X行 更换商品，数量已清零」1 次。

6. 点**挂账** → 同上，框出毕即拆。
7. 留一行数量 0 点保存 → 被「数量必须大于0」拦下，等待框随之消失。
8. 点「清空当前单据」→ 行为与原厂一致（绑定已还原 sys_billempty）。
